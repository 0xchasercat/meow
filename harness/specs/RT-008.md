## Motivation

Many real Node projects depend on native addons (`bcrypt`, `sharp`, `sqlite3`, platform-specific optional deps). Drop-in compatibility fails if `require("*.node")` cannot load. Amendment 003 chooses upstream `deno_napi` rather than a meow-owned N-API implementation.

RT-008 wires `deno_napi` to meow's cache/unpacked-store model: a native addon package/version/member selected by the shared `ResolutionGraph` for the referrer is extracted to a real file and loaded through Deno's N-API machinery via the default materialized project-local `node_modules` symlink tree backed by the global unpacked store.

## Acceptance criteria

### A1 — `deno_napi` is registered

Default runtime mode registers `deno_napi::init(...)` with the services required by Deno's Node/N-API path. The runtime supplies the `PermissionsContainer`, V8 task spawner, external ops tracker, and any uv compatibility state required by the upstream crate.

### A2 — native addons load from real extracted files

When Deno Node resolves a `.node` member inside a cached package, meow ensures the file exists in the immutable unpacked store and is reachable through the project-local symlink tree path handed to `deno_napi`. The loader never requires a copied project `node_modules` fallback.

### A3 — custom native addon loader preserves integrity

If a `deno_napi::DenoRtNativeAddonLoader` is needed, it must:

- map the requested package member to the exact `ResolutionGraph` package/version selected for the referrer;
- extract via `UnpackedStore` / `Cache::read`, preserving cache integrity checks;
- return a stable materialized symlink-tree path suitable for `dlopen` / `LoadLibrary`;
- never silently copy unverified bytes to temp.

### A4 — unsupported addons fail honestly

Deno's N-API supports Node-API addons, not arbitrary legacy V8/NAN addons. Unsupported legacy addons must surface Deno's precise error (or an equally precise meow wrapper) naming the path and unsupported class. Do not claim all native addons work until the corpus proves it.

### A5 — platform/package optionality is Node-compatible

Optional native deps that are not selected for the current platform should behave like Node package resolution would: missing optional platform packages do not abort install/run unless required by user code. Platform-specific package selection remains a package-manager/graph input, not an N-API loader guess.

## Non-goals

- Supporting legacy NAN/V8 binary addons beyond what `deno_napi` supports.
- Copying project `node_modules` as a default `*.node` loading substrate.
- A meow-owned N-API implementation.
- Bypassing cache integrity for temporary files.

## Interface

Conceptual runtime service:

```rust
pub struct MeowNativeAddonLoader {
    pub graph: Arc<ResolutionGraph>,
    pub cache: Arc<Cache>,
    pub unpacked: UnpackedStore,
    pub project_node_modules: PathBuf,
}

impl deno_napi::DenoRtNativeAddonLoader for MeowNativeAddonLoader { ... }
```

Use the exact upstream trait/type signature from `deno_napi` / `denort_helper`; do not introduce a parallel abstraction unless needed to keep meow types out of runtime internals.

## Tests required

- Fixture N-API addon or checked-in minimal `.node` test asset loads through `require(...)` from the materialized `node_modules` symlink tree path.
- Missing addon path errors honestly.
- Unsupported legacy addon fixture reports unsupported legacy/native-addon class, not a panic.
- Cache tamper before extraction fails before `dlopen`.
- No temporary manual native loader shim is used as canonical for N-API integration.

Gates: `drop-in`, `compat`, `lockfile-integrity`, `honesty`, `footprint`.

## Rollout

RT-008 follows RT-007 and LOAD-004 because it depends on Deno Node require resolution and the symlink-tree path bridge. If a first implementation only supports a minimal test addon, it must be labelled as corpus-incomplete; do not market native addon parity until real packages (`bcrypt`, `sharp`, or equivalent) pass, and no manual native loader shim remains canonical.
