## Motivation

Amendment 003 changes the RT-007 strategy. `meow` should not hand-author `node:fs`, `node:path`, `process`, `Buffer`, `http`, etc. Upstream Deno already carries the maintained Node implementation at the same `deno_core` generation. RT-007's job is to register that implementation and remove conflicting meow-owned built-in shims, while preserving meow's package/cache and capability boundaries.

Default install now emits a strict pnpm-style, project-local `node_modules` symlink tree, with each leaf pointing into the global unpacked store. Runtime/tooling should follow these real filesystem paths first; `.meow/deps` remains tooling-only.

Traceability: P2.5's five-minute test fails if a stock app imports Node built-ins and sees meow stubs. Amendment 003 says Deno owns Node semantics; meow owns graph selection, cache integrity, and the symlinked filesystem bridge.

## Acceptance criteria

### A1 — Deno Node extension is the default Node surface

Default runtime mode registers the upstream Deno Node stack needed for built-ins/globals:

- `deno_node` for `node:*` / bare built-ins, `process`, `Buffer`, and Node internal JS;
- `deno_crypto`, `deno_fetch`, and `deno_net` as required dependencies for Deno's Node modules and Web/HTTP/TLS substrate;
- existing `deno_web` / `deno_webidl` / `deno_crypto` ordering remains valid for strict-web and fetch.

`strict-web` remains an explicit opt-in mode that withdraws Node surfaces; default mode is drop-in.

### A2 — manual Node built-ins are retired, not extended

The target state has no meow-authored `js/node/*.ts` polyfill ownership for Node core modules. Manual path/fs and CJS shims may only exist as explicitly marked compatibility debt and must be deleted by RT-007/LOAD-004/RT-008; they MUST NOT be treated as canonical.
Required conflict removals / retargeting:

- `crates/runtime/src/native.rs` no longer maps Node built-ins to `include_str!("js/node/*.ts")` as the canonical source.
- The resolver does not claim a meow-native implementation for built-ins that Deno owns.
- `meow_node` bootstrap does not install competing `process` / `Buffer` globals when `deno_node` owns them.

### A3 — built-in identity follows Node/Deno semantics

All of these work in default mode without user configuration:

```ts
import fs from "fs";
import fs2 from "node:fs";
import path from "path";
console.log(process.cwd(), Buffer.from("ok").toString());
```

Bare built-ins and `node:` specifiers resolve to the same Deno-owned module identity. Unknown `node:*` specifiers error honestly.

### A4 — capability and strict-web boundaries are explicit

Default mode is permissive for drop-in compatibility. Strict-web withdrawal is explicit and testable. Any meow-specific permission/capability interception that remains in front of Deno Node APIs must be documented as a meow policy layer, not as Node semantics.

### A5 — dependency surface is pinned centrally

Workspace pins add the Deno crates needed by this harvest at versions compatible with `deno_core = 0.403`:

- `deno_node = 0.188.0`
- `deno_napi = 0.181.0` (wired by RT-008 / N-API slice, but pinned with the harvest)
- `node_resolver = 0.88.0`
- `deno_fs = 0.160.0`
- `deno_io = 0.160.0`
- `deno_package_json = 0.52.0`
- `deno_process = 0.65.0` if required by the selected `deno_node` init path

No forked Deno crates.

## Non-goals

- Reimplementing Node built-ins in Rust or TypeScript.
- Claiming all Node compatibility before the real-project corpus passes.
- Forcing `meow-cache://` URLs through Deno's path-oriented Node resolver.
- Copying package contents into project `node_modules`; the default compatibility substrate is symlink-only.
- N-API loading itself; RT-008 owns native addon extraction/loading.

## Interface

Runtime extension assembly must grow a Deno Node harvest seam, conceptually:

```rust
pub mod node;

pub struct NodeOptions {
    pub mode: NodeMode,
    pub cwd: PathBuf,
    pub argv: Vec<String>,
    pub env: BTreeMap<String, String>,
    pub deno_node_services: Option<DenoNodeServices>,
}

pub struct DenoNodeServices {
    // Built from meow's ResolutionGraph + materialized node_modules symlink tree.
    pub node_ext_init: deno_node::NodeExtInitServices<...>,
    pub fs: deno_fs::FileSystemRc,
}

pub fn node::extensions(opts: NodeOptions) -> Vec<deno_core::Extension>;
```

Exact generic names may differ, but the implementation MUST use upstream `deno_node::init(...)`, not copied JS/polyfills.

## Implementation sketch

1. Add compatible Deno dependency pins in the workspace and runtime crate.
2. Register Deno's required base extensions in the correct order (`deno_webidl`/`deno_web`/`deno_io`/`deno_fs`/`deno_node`, plus already-used fetch/crypto/net where needed).
3. Build minimal default services for local-file execution, then replace package-folder lookup with the symlink bridge from LOAD-004, wiring Deno Node to the materialized `node_modules` tree.
4. Remove or quarantine manual `crates/runtime/src/js/node/*` mappings and bootstrap globals that conflict with Deno Node.
5. Keep `meow:*` native modules and `meow:internal/*` separate from Node built-ins.

## Tests required

- `import "node:fs"`, `import "fs"`, `import "node:path"`, `import "path"` work in default mode.
- `process` and `Buffer` globals are Deno-owned and usable.
- `strict-web` does not expose ambient Node globals.
- Unknown built-in errors honestly.
- Default install creates a strict pnpm-style project-local `node_modules` symlink tree backed by the unpacked store and used for Deno Node resolution.
- Compile-time check: no manual built-in source is used as canonical `node:*` implementation.

Gates: `drop-in`, `compat`, `resolver-parity`, `footprint`, `honesty`.

## Rollout

RT-007 is the first harvest stage. It may land before full PnP package resolution is connected, but it must not deepen manual polyfills. Any temporary path/fs/CJS compatibility debt must be deleted during RT-007/LOAD-004/RT-008, or the remaining gap must be explicitly recorded.
